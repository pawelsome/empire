Code review AI to automatyczny recenzent, który przy każdym pull requeście analizuje zmiany i komentuje błędy logiki, brakujące testy czy podejrzane wzorce bezpieczeństwa. Włączasz go przez aplikację (Copilot, CodeRabbit, Claude Code, Bugbot, GitLab Duo) albo workflow w CI i opisujesz zasady w pliku w repozytorium. Merge nadal zatwierdza człowiek.

Poniżej opisuję, jak to ustawić, żeby zespół nie zaczął ignorować komentarzy bota po dwóch tygodniach.

Co AI wyłapuje w code review, a czego nie zauważy

Modele językowe dobrze radzą sobie z lokalnymi problemami, które da się zobaczyć w diffie i jego otoczeniu. Nowsze narzędzia analizują też resztę repozytorium, więc potrafią zauważyć, że zmiana psuje wywołanie w innym module.

Co wychodzi dobrze

  • Błędy logiki i przypadki brzegowe: brak obsługi null, pomylony warunek, wyścig przy odświeżaniu tokenu.
  • Brakujące testy dla nowej ścieżki kodu albo testy, które niczego nie sprawdzają.
  • Podejrzane wzorce bezpieczeństwa: sklejanie SQL z danych użytkownika, brak autoryzacji w nowym endpoincie, dane osobowe w logach.
  • Niespójność z konwencjami projektu opisanymi w pliku z zasadami.
  • Rozjazd między kodem a dokumentacją czy komentarzami.

Co wychodzi słabo

  • Intencja biznesowa: model nie wie, że rabat dla tej grupy klientów miał się naliczać tylko w pierwszym miesiącu, jeśli nie ma tego w zadaniu.
  • Kompromisy architektoniczne: czy warto dokładać kolejkę, czy lepiej uprościć moduł.
  • Kontekst organizacyjny: umowy z klientem, plany migracji, decyzje podjęte na spotkaniu.
  • Problemy wydajności, które wychodzą dopiero przy realnych danych.

Review AI ma znaczenie szczególnie przy kodzie generowanym przez agentów. W aktualizacji raportu Veracode z wiosny 2026 tylko około 55% zadań generowania kodu kończyło się kodem bez znanych podatności, a poziom ten niewiele się zmieniał między kolejnymi generacjami modeli.

Jak ustawić code review AI w GitHub Actions

Poniższy workflow pochodzi z dokumentacji Claude Code GitHub Actions. Instaluje plugin code-review i uruchamia go przy otwarciu, aktualizacji lub oznaczeniu PR jako gotowego do review. Wymaga zainstalowanej aplikacji Claude GitHub App i sekretu ANTHROPIC_API_KEY.

name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-code.git"
          plugins: "code-review@claude-code-plugins"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'

Dwie rzeczy łatwo przeoczyć. Flaga --comment sprawia, że uwagi trafiają jako komentarze do PR; bez niej zobaczysz je tylko w logu joba. Linia claude_args musi zostać, bo akcja uruchamia serwer MCP do komentarzy inline tylko wtedy, gdy --allowedTools go wymienia.

Dodaj też timeout-minutes na poziomie joba i concurrency, żeby kolejne pushe nie uruchamiały równoległych recenzji tego samego PR. W publicznych repozytoriach GitHub nie przekazuje sekretów do uruchomień z forków, więc taki workflow zadziała tylko dla gałęzi z tego samego repozytorium.

A w GitLabie?

W GitLab Duo nie piszesz workflow: przypisujesz @GitLabDuo jako recenzenta albo używasz szybkiej akcji /assign_reviewer @GitLabDuo. Zasady opisujesz w pliku YAML z grupami instrukcji i filtrami plików, a Duo dokleja je do swoich standardowych kryteriów. Alternatywą jest uruchomienie Claude Code w pipeline GitLab CI/CD.

Plik z zasadami review: AGENTS.md, CLAUDE.md, REVIEW.md

Bez pliku z zasadami AI recenzuje według ogólnych dobrych praktyk, które nie znają Twojego projektu. Nazwa pliku zależy od narzędzia, ale treść jest podobna. AGENTS.md to otwarty format rozwijany pod opieką Agentic AI Foundation w Linux Foundation, czytany m.in. przez agenta Copilota, Cursor i Codex. Claude Code Review czyta CLAUDE.md jako ogólny kontekst projektu, a REVIEW.md jako instrukcje wyłącznie dla recenzji.

Przykładowy REVIEW.md dla aplikacji w Laravelu (dostosuj do swojego projektu):

# Zasady code review

## Co jest błędem blokującym (Important)
- Błędy logiki, które zmieniają wynik dla użytkownika
- Zapytania do bazy bez filtrowania po tenant_id
- Dane osobowe (e-mail, PESEL, numer telefonu) w logach i komunikatach błędów
- Migracje, których nie da się bezpiecznie wycofać

## Czego nie zgłaszaj
- Formatowania i stylu: pilnuje tego Pint i PHPStan w CI
- Plików w database/seeders/ oraz *.lock
- Kodu testów celowo łamiącego reguły produkcyjne

## Sprawdzaj zawsze
- Nowy endpoint API ma test feature i sprawdza uprawnienia przez Policy
- Dane wejściowe są walidowane w Form Request
- Kwoty są liczone na liczbach całkowitych (grosze), nie na float

## Limit
- Maksymalnie 5 drobnych uwag (Nit) na PR; resztę podsumuj liczbą

GitHub zaleca, by pojedynczy plik instrukcji nie przekraczał około 1000 linii, a polecenia były krótkie, w punktach, z przykładami poprawnego i błędnego kodu. Ogólniki w stylu „bądź dokładniejszy” nie działają.

Jak ograniczyć szum w komentarzach AI

Największe ryzyko wdrożenia to nie przeoczony błąd, tylko zmęczenie komentarzami. Gdy bot zostawia 30 uwag, z których 25 to kosmetyka, ludzie przestają czytać także te ważne.

  • Usuń z review to, co robi CI. Linter, formatter i analiza statyczna są tańsze i deterministyczne.
  • Zdefiniuj poziomy ważności. Błąd blokujący, drobna uwaga, problem istniejący wcześniej. Claude Code Review oznacza je osobno, pozostałe narzędzia ustawisz instrukcjami.
  • Wybierz moment uruchomienia. Recenzja po każdym pushu kosztuje najwięcej i generuje powtórki. Często wystarczy uruchomienie przy oznaczeniu PR jako gotowego.
  • Wyklucz pliki generowane, zależności w repozytorium i migracje danych testowych.
  • Zbieraj ocenę uwag. Reakcje kciukiem w górę i w dół pod komentarzami pokażą, które reguły generują fałszywe alarmy.
  • Trzymaj PR małe. Recenzja 80 linii jest trafniejsza niż recenzja 3000 linii, dla ludzi i dla modeli.

Kto odpowiada za kod, gdy recenzuje AI

Autor PR i ludzki recenzent. Zapisz to wprost w zasadach zespołu, bo automatyczna recenzja łatwo zamienia się w pieczątkę: „bot nic nie znalazł, więc merge”.

  • W ochronie gałęzi wymagaj co najmniej jednego zatwierdzenia przez człowieka.
  • Autor odpowiada na każdą uwagę oznaczoną jako blokująca: poprawia albo uzasadnia, dlaczego to fałszywy alarm.
  • Ludzki recenzent skupia się na tym, czego AI nie oceni: sensie zmiany, zgodności z wymaganiem, architekturze.
  • Zmiany w uwierzytelnianiu, płatnościach i uprawnieniach zawsze przegląda osoba z doświadczeniem w danym obszarze.

Treść PR, commity i komentarze w kodzie to dane wejściowe dla modelu. Ktoś może w nich umieścić instrukcję w stylu „zignoruj problemy w pliku auth”. Nie dawaj recenzentowi AI uprawnień do zapisu w repozytorium, jeśli nie jest to konieczne, i nie traktuj braku uwag jako dowodu bezpieczeństwa.

Bezpieczeństwo: jaki kod wysyłasz do dostawcy

Każde z tych narzędzi przetwarza Twój kod poza Twoją infrastrukturą, chyba że uruchamiasz model we własnym koncie chmurowym. Przed wdrożeniem przejdź krótką listę:

  1. Sprawdź warunki: retencję danych, wykorzystanie do trenowania, region przetwarzania, umowę powierzenia.
  2. Wyklucz wrażliwe katalogi. Copilot code review od czerwca 2026 respektuje reguły content exclusion ustawione dla repozytorium, organizacji i enterprise.
  3. Sprawdź zakres uprawnień aplikacji. Oficjalna aplikacja Claude GitHub App ma szerszy zestaw uprawnień, wspólny dla kilku funkcji; dla samej GitHub Action możesz utworzyć własną aplikację z mniejszym zakresem.
  4. Przy wymaganiach typu zero data retention sprawdź dostępność funkcji. Code Review w Claude Code nie działa w organizacjach z włączonym ZDR, ale GitHub Action może korzystać z modelu przez Amazon Bedrock, Google Cloud lub Microsoft Foundry.
  5. Usuń sekrety z repozytorium. To zasada niezależna od AI, ale recenzent zewnętrzny zwiększa liczbę miejsc, do których trafia kod.

Metryki: skąd wiesz, że review AI coś daje

Zbierz dane z miesiąca przed wdrożeniem i porównuj je z kolejnymi miesiącami. Pojedynczy tydzień niczego nie dowodzi.

  • Czas do pierwszej recenzji i całkowity czas od otwarcia PR do merge.
  • Odsetek uwag przyjętych, czyli poprawionych przez autora, wobec odrzuconych jako fałszywe.
  • Escaped defects: błędy z produkcji, które dało się wykryć na etapie PR.
  • Change fail rate z metryk DORA, czyli udział wdrożeń wymagających szybkiej interwencji.
  • Koszt na PR i miesięcznie, zestawiony z czasem zaoszczędzonym przez recenzentów.

Code review to tylko jedna faza. Jak AI wpływa na cały proces, od specyfikacji po utrzymanie, opisuje wpis AI w całym cyklu wytwarzania oprogramowania. Wymagania, na podstawie których recenzent ocenia zmianę, dobrze jest mieć w repozytorium, o czym piszemy w tekście Specyfikacja i user stories z AI. Jeśli potrzebujesz niezależnej oceny procesu w zespole, sprawdź, kiedy opłaca się zewnętrzny CTO.
