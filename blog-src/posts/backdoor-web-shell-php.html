Backdoor PHP to ukryty fragment kodu, który pozwala atakującemu wrócić na serwer nawet po usunięciu widocznego wirusa. Web shell to jego rozbudowana odmiana: panel do przeglądania plików i wykonywania poleceń przez przeglądarkę. Żeby się ich pozbyć, porównaj pliki z czystymi wersjami, przeszukaj kod i logi, a potem zamknij lukę i wymień hasła.

Czym jest backdoor PHP, a czym web shell

Oba pojęcia opisują to samo zjawisko w różnej skali. Backdoor bywa jedną linijką, która przyjmuje kod z parametru żądania albo z ciasteczka i go wykonuje. Web shell to pełne narzędzie: menedżer plików, konsola poleceń systemowych, dostęp do bazy danych. NSA i australijskie ASD opisują web shell jako złośliwe oprogramowanie na serwerze WWW, które pozwala wykonywać dowolne polecenia przesyłane przez HTTP lub HTTPS.

Backdoor nie musi być osobnym plikiem. W praktyce spotkasz:

  • plik o niewinnej nazwie, udający element systemu, cache albo tłumaczenia,
  • kilka linijek doklejonych do prawdziwego pliku, np. index.php, wp-config.php czy functions.php,
  • fałszywą wtyczkę, która ukrywa się na liście w panelu,
  • kod zapisany w bazie danych i wykonywany przez inną część aplikacji,
  • dodatkowe konto administratora albo mechanizm „awaryjnego” logowania,
  • zadanie cron lub zmodyfikowany plik, który odtwarza usunięte elementy.

Przykład z 2025 roku: Wordfence opisało fałszywą wtyczkę WP-antymalwary-bot.php. Ukrywała się w panelu, pozwalała zalogować się jako administrator zapytaniem z zaszytym w kodzie hasłem, a zmodyfikowany wp-cron.php odtwarzał ją i ponownie aktywował po usunięciu.

Dlaczego strona zaraża się ponownie po usunięciu wirusa

Widoczne skutki włamania, takie jak spam, przekierowania czy fałszywe formularze płatności, to ładunek. Backdoor to sposób, żeby ten ładunek wgrać ponownie. Jeśli usuniesz tylko ładunek, atakujący wraca tą samą drogą i po jakimś czasie masz powtórkę, często w innym miejscu.

Atakujący lubią zostawiać kilka furtek. W lutym 2025 roku Sucuri opisało infekcję, w której plik w mu-plugins pobierał zaszyfrowany ładunek z wp-content/uploads/2024/12/index.txt, a niezależnych backdoorów było więcej, żeby dostęp przetrwał usunięcie jednego z nich. Stąd prosta zasada: po znalezieniu pierwszego szukaj dalej. Z tego samego powodu wraca japoński spam SEO i złośliwe przekierowania.

Jak znaleźć backdoor PHP w plikach

Polecenia w tej sekcji tylko czytają i wyświetlają wyniki. Uruchamiaj je po zrobieniu pełnej kopii plików i bazy, najlepiej na kopii strony. Niczego nie kasuj, dopóki nie zabezpieczysz dowodów.

Porównaj pliki z czystymi wersjami

To metoda z najmniejszą liczbą fałszywych alarmów, bo nie zgaduje, tylko porównuje. Wytyczne NSA wskazują porównanie z wersją znaną jako dobra jako najskuteczniejszy sposób wykrywania większości web shelli. W WordPressie WP-CLI sprawdza rdzeń i wtyczki z repozytorium WordPress.org względem oficjalnych sum kontrolnych. Dodawaj flagi --skip-plugins --skip-themes, żeby nie uruchamiać podejrzanego kodu podczas ładowania WordPressa.

# Rdzeń WordPressa: zmienione pliki i pliki, których nie powinno być
wp core verify-checksums --include-root --skip-plugins --skip-themes

# Wtyczki pobrane z repozytorium WordPress.org
wp plugin verify-checksums --all --skip-plugins --skip-themes

# Aplikacja wdrażana z Gita: zmiany względem repozytorium
git status --porcelain
git diff --stat

Sumy kontrolne nie obejmują motywów, wtyczek premium ani katalogu uploads. Wtyczki komercyjne pobierz ponownie od producenta w tej samej wersji i porównaj katalogi poleceniem diff -rq czysta/ serwer/.

Szukaj podejrzanych funkcji i zaciemnionego kodu

Backdoor musi w którymś momencie zamienić tekst na wykonywany kod albo polecenie systemowe. Te funkcje i konstrukcje warto rozpoznawać od razu:

FunkcjaDlaczego jest podejrzana
evalWykonuje dowolny kod PHP przekazany jako tekst
assertPrzed PHP 8.0 wykonywała napis jak kod; w starych infekcjach nadal ją spotkasz
preg_replace z modyfikatorem /eWykonywał wynik zamiany jako kod; nie działa od PHP 7.0, ale zostaje w starym malware
create_functionTworzyła funkcję z napisu przez eval; usunięta w PHP 8.0
base64_decode, gzinflate, gzuncompress, str_rot13Same w sobie niegroźne, ale służą do rozpakowywania ukrytego ładunku, zwykle w kilku warstwach
system, exec, shell_exec, passthru, proc_open, popenWykonywanie poleceń systemowych
file_put_contents, move_uploaded_file z danymi z żądaniaZapisywanie nowych plików na serwerze
 
# Pliki PHP z typowymi funkcjami backdoorów (spodziewaj się fałszywych trafień)
grep -rlE --include="*.php" '(eval|assert|gzinflate|gzuncompress|str_rot13)[[:space:]]*\(' /sciezka/do/strony

# Dane z żądania przekazywane prosto do wykonania
grep -rnE --include="*.php" '(eval|assert|system|shell_exec|passthru)[[:space:]]*\([[:space:]]*\$_(POST|GET|REQUEST|COOKIE|SERVER)' /sciezka/do/strony

# Bardzo długie linie, typowe dla zaciemnionego kodu
find /sciezka/do/strony -name "*.php" -exec awk 'length($0) > 5000 { print FILENAME; exit }' {} \;

Legalne wtyczki też używają base64_decode czy exec, więc wynik to lista do przejrzenia. Liczy się kontekst: dane z $_POST lub $_COOKIE trafiające do dekodowania i wykonania, zmienne o losowych nazwach, jedna gigantyczna linia. Grep nie złapie też wszystkiego. W infekcji opisanej przez Sucuri nazwę funkcji sklejano z kawałków ('ba'.'se'.'64_de'.'co'.'de'), więc prosty wzorzec jej nie wykryje.

Sprawdź uploads i świeżo zmienione pliki

Katalog na przesyłane pliki nie powinien zawierać żadnego PHP. Szukaj też kodu PHP ukrytego w plikach z inną końcówką, bo można go dołączyć przez include z dowolnego miejsca.

# Pliki wykonywalne w uploads
find /sciezka/do/strony/wp-content/uploads -type f \( -iname "*.php*" -o -iname "*.phtml" -o -iname "*.phar" \)

# Kod PHP ukryty w obrazkach, plikach .txt, .ico itp.
grep -rl "<?php" /sciezka/do/strony/wp-content/uploads

# Pliki PHP zmienione w ostatnich 14 dniach, od najnowszych, według ctime
find /sciezka/do/strony -type f -name "*.php" -ctime -14 -printf '%C+ %p\n' | sort -r

# mu-plugins i dyrektywy PHP ładujące plik przed każdym skryptem
ls -la /sciezka/do/strony/wp-content/mu-plugins/
grep -rn "auto_prepend_file\|auto_append_file" --include=".user.ini" --include=".htaccess" --include="php.ini" /sciezka/do/strony

Datę modyfikacji (mtime) atakujący zmienia jednym poleceniem touch, żeby plik wyglądał na stary. Czas zmiany metadanych (ctime) jest trudniejszy do podrobienia, dlatego filtruj po nim. Gdy znajdziesz pierwszy zainfekowany plik, sprawdź jego ctime i wyszukaj inne pliki zmienione w tym samym oknie czasowym.

Konta, zadania cron i baza danych

wp user list --role=administrator --fields=ID,user_login,user_email,user_registered --skip-plugins --skip-themes
wp cron event list --skip-plugins --skip-themes
crontab -l
wp db search 'eval(' --all-tables --skip-plugins --skip-themes
wp db search 'base64_decode' --all-tables --skip-plugins --skip-themes

Co pokażą logi serwera

Pliki mówią, co zostało zmienione. Logi mówią, jak atakujący wszedł i czy nadal korzysta z dostępu. Poproś hosting o logi dostępu z możliwie długiego okresu, bo są rotowane i po jakimś czasie znikają.

Szukaj przede wszystkim:

  • żądań POST do plików, które nie powinny ich przyjmować, zwłaszcza w uploads, w głębi katalogów wtyczek albo do plików o losowych nazwach,
  • odpowiedzi 200 dla plików PHP, których nie ma w czystej instalacji,
  • adresów odwiedzanych przez bardzo małą liczbę adresów IP lub User-Agentów, bez nagłówka Referer,
  • zapytań tuż przed ctime pierwszego zainfekowanego pliku, bo tam zwykle widać wykorzystanie luki.
# Adresy najczęściej wywoływane metodą POST (format logu combined)
grep '"POST ' /var/log/apache2/access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -30

# Żądania do plików PHP w uploads
grep -E '"(GET|POST) /wp-content/uploads/[^" ]*\.php' /var/log/apache2/access.log

# Wszystko, co robił jeden podejrzany adres IP (tu adres z puli dokumentacyjnej)
grep '^203\.0\.113\.45 ' /var/log/apache2/access.log

Tak samo podchodzą do tematu wytyczne NSA i ASD: szukanie rzadko odwiedzanych adresów, nietypowych klientów i brakujących nagłówków Referer. Na serwerze z dostępem roota warto też sprawdzić, czy proces serwera WWW nie uruchamiał poleceń w rodzaju whoami czy sh, co pokażą reguły auditd. Przy kilku serwerach ręczny grep przestaje wystarczać i wtedy przydaje się centralne zbieranie logów, o którym piszemy w artykule o monitoringu logów w ELK i Grafanie.

Jak bezpiecznie usunąć backdoor i web shell

Kroki poniżej obejmują usuwanie plików i kont. Wykonaj je dopiero po zrobieniu pełnej kopii plików, bazy i logów przechowywanej poza serwerem. Jeśli dane klientów mogły wyciec, ta kopia będzie potrzebna do oceny naruszenia.

  1. Włącz tryb serwisowy lub ogranicz dostęp do strony na czas prac.
  2. Podejrzane pliki przenieś do kwarantanny poza katalogiem publicznym zamiast od razu kasować, np. mkdir -p ~/kwarantanna && mv plik.php ~/kwarantanna/.
  3. Rdzeń, wtyczki i motywy zainstaluj od nowa z oficjalnych źródeł. Nie czyść pojedynczych linijek, jeśli możesz podmienić cały plik.
  4. Usuń nieznane konta administratorów, zadania cron i wpisy auto_prepend_file.
  5. Wymień wszystkie sekrety: hasła do hostingu, SSH, SFTP i bazy, klucze w wp-config.php, klucze API bramek płatności i usług zewnętrznych.
  6. Zamknij lukę, przez którą wszedł atakujący: zaktualizuj lub usuń podatną wtyczkę, wyłącz nieużywane konta FTP.
  7. Zablokuj wykonywanie PHP w katalogu uploads i ponownie przeskanuj całość.
# wp-content/uploads/.htaccess (Apache 2.4)
<FilesMatch "\.(php|phtml|phar)$">
    Require all denied
</FilesMatch>
# nginx: w bloku server, przed blokiem przekazującym pliki .php do PHP-FPM
location ~* ^/wp-content/uploads/.*\.(php|phtml|phar)$ {
    deny all;
}

Jeśli web shell działał na VPS lub serwerze dedykowanym, a atakujący mógł podnieść uprawnienia, nie ufaj już temu systemowi. Bezpieczniej postawić serwer od nowa i wgrać na niego wyczyszczoną aplikację.

Jak nie dopuścić do ponownej infekcji

  • Monitoruj integralność plików. Alert o nowym pliku PHP w uploads albo zmianie w wp-config.php daje czas na reakcję, zanim ktoś zobaczy spam. Takie reguły skonfigurujesz np. w Wazuhu, o czym piszemy w artykule Wazuh w małej firmie.
  • Rozdziel uprawnienia: użytkownik, na którym działa PHP, nie powinien móc zapisywać plików kodu. Zapis zostaw tylko tam, gdzie jest potrzebny.
  • Wyłącz edycję plików z panelu i instaluj rozszerzenia wyłącznie z zaufanych źródeł, nigdy z „darmowych” kopii wtyczek premium.
  • Rozważ wyłączenie w php.ini funkcji wykonujących polecenia systemowe (disable_functions), jeśli aplikacja ich nie potrzebuje. Przetestuj to najpierw na kopii strony.
  • Oceń, czy doszło do naruszenia ochrony danych osobowych. Jeśli tak i istnieje ryzyko dla osób, których dane dotyczą, masz 72 godziny od stwierdzenia naruszenia na zgłoszenie do UODO.

Pełną listę ustawień znajdziesz w checkliście zabezpieczenia WordPressa, a jeśli dopiero zauważyłeś pierwsze objawy, zacznij od artykułu zainfekowany WordPress: objawy i pierwsza godzina. Szukanie backdoorów i analizę powłamaniową wykonujemy też zawodowo.
